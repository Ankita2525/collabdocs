Records how AI was actually used. Entries are added only for things that really happened.

## Tools used
Two AI tools were used in this assessment. **This file was written by Claude Code, which can only document its own work and has no visibility into the candidate's ChatGPT conversations.** The ChatGPT description below was supplied by the candidate and is reproduced as such; Claude Code has not verified it and adds nothing to it.

**1. Claude Code (Claude Sonnet 5.5), Claude desktop app, Code tab: documented in detail in this file.** It planned (in plan mode), wrote the application code, tests, verification harnesses and the documentation, and ran commands in the candidate's project folder.
- Tools Claude Code ran: `npm`/Next.js/Vitest/ESLint/TypeScript, `curl` and small Python/Node scripts against the real Supabase database and the Vercel deployment, `git` and the `gh` CLI (commit, push, read commit status), and the CommonMark reference parser `commonmark` (installed only in a scratch directory, not in the project) for validating Markdown export.
- The built-in browser was tried once for a visual check and hung, so it was not used for any verification.
- Claude Code did not use any other AI service, and no AI API is called from the application itself.

**2. ChatGPT: planning, prompt-engineering and review assistant (description provided by the candidate; not verifiable by Claude Code).**
ChatGPT was used throughout the assessment as a complementary assistant alongside Claude Code. Per the candidate, its contributions were:
- Analysing the assessment requirements, evaluation criteria and mandatory deliverables.
- Proposing the initial technology stack, architecture and time-boxed implementation strategy.
- Preparing structured prompts for Claude Code across the implementation milestones (so the requirements text that started the Claude Code session originated from this work).
- Reviewing Claude Code's original and revised implementation plans, and recommending early deployment, API-level authorization testing, atomic concurrency protection and separate submission documentation.
- Providing guidance for Supabase, GitHub and Vercel configuration.
- Reviewing Claude Code's milestone reports and identifying pending verification requirements; preparing manual browser testing checklists.
- Reviewing screenshots of the deployed M2 dashboard and recommending UI improvements.
- Helping prioritise core functionality before optional enhancements, defining the requirements and acceptance criteria for Markdown and PDF export, and reviewing the submission requirements and final delivery workflow.

**Decisions and iterations (candidate-reported).** The initial plan was revised to reserve more time for deployment, documentation and submission. Saving during browser unload was rejected in favour of explicit save, autosave and unsaved-change warnings. Real-time collaboration, commenting and version history were deprioritised to protect core functionality. ChatGPT initially recommended against additional stretch features; the candidate later decided to include Markdown export and browser-based PDF (print) export within a separate timebox.

**Verification boundaries.** ChatGPT reviewed requirements, plans, screenshots and implementation reports provided in the conversation. It did not modify the repository, execute the project's automated tests, query the database or run production API checks. Implementation and all automated verification recorded in this file were done by Claude Code; manual browser checks are attributed only to the person who performed them (the candidate, as stated under each entry).

## Meaningful contributions
**Division of work (Claude Code and the candidate; ChatGPT's planning and review role is described by the candidate in the section above).** The candidate set the requirements and constraints (with ChatGPT's help, per the candidate), revised the plan, approved every milestone and every push, created and configured the Supabase, GitHub and Vercel accounts and projects, and performed (and reports) the browser verification. Claude wrote essentially all code, tests, harnesses and documents. Nothing here claims browser verification that the candidate has not reported.

**What Claude contributed, concretely:**
- *Plan and architecture:* the four-hour plan with explicit simplifications (no ORM, no Supabase Auth or RLS-based rules, server-side sessions, content as Tiptap JSON), later revised on the candidate's instructions (see below).
- *Authorization:* one `getAccess`/`can` function and one `loadDocumentFor` choke point used by every document route; 404 for no access vs 403 for insufficient rights; API-level tests that call the real route handlers, plus a mutation check showing the tests fail if authorization is weakened.
- *Data integrity:* atomic version compare-and-set in a single `UPDATE ... WHERE version = $base`; server-side validation of saved content against the real Tiptap schema plus explicit attribute checks (found necessary by a failing test: the schema alone accepted heading level 4).
- *Production bug found and fixed:* concurrent queries hung against Supabase's pooler; reproduced outside Next.js and fixed with `max_pipeline: 1`.
- *Features:* rich-text editor with debounced autosave and honest save states; sharing with viewer/editor roles and handling of access lost while an editor is open; `.txt` import with strict validation; Markdown export and Print / Save as PDF; UI identity and polish.
- *Reliability reviews:* recovery from a "false conflict" after a lost save response; list-of-edge-cases review of autosave, stale writes and revocation.
- *Verification tooling:* curl/Python harnesses run against the real database and production, before/after database snapshots (with content hashes) proving existing documents were untouched, and a randomized round-trip of the Markdown serializer against the CommonMark reference parser.

## Suggestions changed or rejected
**Candidate's direction changed Claude's plan or behaviour** (the candidate reports that early deployment, API-level authorization tests, atomic concurrency protection and separate submission documents were recommended by ChatGPT's review of Claude Code's plan; Claude Code adopted them as instructed):
- Plan review (before implementation): the initial plan was revised on the candidate's direction. Added an atomic DB-level stale-write guard, Tiptap-schema validation of stored content, API-level authorization tests, removal of any save-on-`beforeunload`, labelling of demo authentication as non-production, `.txt`-first import, and a reserved final 40 minutes for submission.
- Stretch features were gated: only document export was approved (Markdown first, PDF only if it did not add risk, as a separate revertable commit, pushed only after approval). Every push was approved by the candidate.
- The candidate required that test scripts never delete candidate- or reviewer-created documents; cleanup became "delete by id of documents created in the same run", with before/after snapshots.

**Claude changed its own approach because evidence contradicted it:**
- Pool settings `max:1` with default pipelining hung under concurrency → `max_pipeline: 1`, `max: 3`.
- Schema-only validation of content was insufficient (heading level) → added attribute validation.
- First owner-wide cleanup helper deleted all of Alice's documents while the shared database could hold manual test data → removed; scoped cleanup; snapshots.
- The M5 import limit (1 MB file) did not fit the 1 MB document cap once converted → document cap raised to 2 MB, with the remaining edge case (very many short lines) documented rather than hidden.
- The first Markdown serializer wrote one delimiter pair per text node; a randomized check against the CommonMark reference parser failed 28 of 600 documents → rewritten as run-based marks with flanking validation and an HTML fallback.
- Wrong hand-written expectations in my own tests were corrected after reasoning (and, for Markdown, after the reference-parser check), not simply edited to match the output.
- Replaced the base-ui `Select` with native `<select>` in the share dialog to avoid API risk.

**Considered and not done (documented limitations or out of scope):** server-generated PDF (Print / Save as PDF is browser-based), Markdown import, real authentication, real-time collaboration, version history, comments.

**Mistake disclosed:** during M1 a command meant to mask the database connection string printed most of the password into the session transcript. It should be rotated if that has not been done; this is recorded under the M1 entry and in the Git hygiene audit.
